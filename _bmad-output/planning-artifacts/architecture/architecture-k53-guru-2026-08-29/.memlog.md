- (version) Backend targets net9.0 (existing template reality). .NET 10.0.11 is now the latest LTS and .NET 9 reaches EOL Nov 2026 - upgrade flagged as Deferred.
- (version) Flutter 3.47.2 stable / Dart 3.13.2 verified current (2026-08-27) for the new mobile client.
- (constraint) ADOPTED paradigm: Clean Architecture + CQRS(MediatR) already established in src/K53Guru (Domain <- Application <- Infrastructure/Server.UI). Ratified, not re-derived.
- (constraint) ADOPTED: no external REST API exists yet - only Blazor Server + auth minimal-APIs. The learner content API is net-new and is the load-bearing new boundary.
- (constraint) ADOPTED backend stack from project.md: EF Core 9 (sqlite/sqlserver/npgsql), FusionCache pipeline, Ardalis.Specification, FluentValidation, AutoMapper, Serilog, MudBlazor Admin, IApplicationDbContextFactory per-op contexts.
- (direction) Dependency direction: Domain <- Application <- {Infrastructure, Server.UI(Admin), Api}. The Flutter client is a separate bounded context depending ONLY on the versioned HTTP API contract, never on DB/Blazor/domain types.
- (decision) Client-server boundary: Flutter app communicates ONLY via a versioned REST/JSON HTTP API served by the backend; it bundles no content and never touches DB/Blazor. Binds all CAPs; prevents client and backend diverging on data shape or the app embedding a stale content copy.
- (decision) API surface: new content API as ASP.NET Core controllers under /api/v1, delegating to the SAME Application-layer MediatR handlers as the Admin Panel - zero business logic in controllers. Prevents Admin-preview and API-delivery computing composition/scoring on two divergent code paths.
- (decision) Fidelity authority: test composition (randomisation, section assembly, combination handling) and scoring/pass-fail (per-section cut-offs, per-code independent grading, partial pass) are computed SERVER-SIDE ONLY in Domain/Application, driven by config data. The Flutter client never computes pass/fail. Binds CAP-4,5,6,8; prevents client and server disagreeing on outcome and fidelity rules drifting.
- (decision) Attempt snapshot: an Attempt captures its full question set (questions, options, correct keys, order, section structure) immutably at start; admin content edits apply only to later attempts and never mutate an in-flight attempt. Binds CAP-4,6; prevents a live attempt changing under the learner or two attempts sharing mutable question refs.
- (decision) Answer confidentiality: in Test mode the API delivers questions WITHOUT correct keys or explanations; the client submits responses and the server returns only per-section/per-code results. Practice mode may return correctness+explanation inline. Binds CAP-6,8; prevents leaking answers to a cold simulation and client-side grading. Security invariant.
- (decision) Road-sign catalog is foundational seeded reference data (official legislative codes) loaded via the Infrastructure initializer; questions reference signs by sign_ref (legislation code), never embedded images or ad-hoc labels; a sign_ref must resolve against the catalog or is rejected. Binds CAP-3,7; prevents orphaned refs, ad-hoc labels, and duplicate sign sources.
- (decision) Import validation boundary: CSV/JSON import validates every row against the question schema AND the sign catalog before persistence, all-or-nothing per row; a malformed or unresolved row is rejected with the offending row identified, never partially stored. Reuses the existing IExcelService/import-command pattern. Binds CAP-2,7; prevents any broken question ever reaching a learner.
- (decision) Two-axis content model: every question carries (a) applicable code(s) in {Code1,Code2,Code3} and (b) a shared-vs-code-specific class (Rules and Signs = shared; Vehicle Controls = code-specific). Section order is fixed Rules->Signs->Controls; randomisation is intra-section only. A combination sitting answers shared sections once and adds one controls module per selected code. Binds CAP-5,6; prevents mis-composed sittings and shared sections being duplicated in a combination.
- (decision) Learner identity is a self-custodied client-generated UUIDv4 sent as an opaque key on API calls - no accounts, no PII, no ASP.NET Identity for learners; the Admin Panel keeps the existing Identity as a separate auth domain. Profile data is keyed by the UUID; rate-limit to deter enumeration. Binds CAP-9; prevents learner identity leaking into the Identity system or any PII collection.
- (decision) Configurable fidelity parameters: per-code question counts, pass marks, time limits, and section definitions are stored as data (config entities seeded from test-structure.md), not hardcoded. Binds CAP-6; prevents hardcoded fidelity logic and Admin/API divergence. Defaults are provisional pending confirmation against a live DLTC/CLLT terminal.
- (decision) API DTO contract: API responses use explicit versioned DTOs and never expose EF entities or domain events; a breaking change bumps the /api/vN segment. Binds all API CAPs; prevents the client coupling to internal schema and silent breaking changes.
- (decision) Two authorization domains: Admin Panel author/import/publish uses existing ASP.NET Identity + roles; the learner API serves ONLY published content anonymously (read) and accepts attempt submissions keyed by the learner UUID. Binds CAP-1,9; prevents draft content leaking to learners and unauthenticated writes to admin content. [ASSUMPTION] admin auth model - SPEC open question.
- (decision) Flutter client paradigm: layered app - presentation (screens/widgets) -> state (Riverpod) -> repository (typed API client + local cache) -> models. Screens never call HTTP directly; all backend access goes through the repository layer against the versioned DTO contract. Binds CAP-5,6,8,9; prevents ad-hoc HTTP calls and business logic leaking into widgets. [ASSUMPTION] Riverpod as state mgmt.
- (decision) Operational envelope: backend containerized via existing docker-compose; PostgreSQL as the production DB provider (Migrators.PostgreSQL present); road-sign static assets served from the existing MinIO/object store or bundled; Flutter app distributed via app stores. [ASSUMPTION] Postgres prod + MinIO for sign images.
- (assumption) Online-first client: test content and attempt submission require connectivity; a thin repository cache smooths reads but offline test-taking is NOT in v1 scope (SPEC open question). Revisit if offline sittings are required.
