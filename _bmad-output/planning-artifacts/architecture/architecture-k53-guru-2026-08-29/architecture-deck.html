Design paradigm

Clean Architecture + CQRS — ratified, not reinvented

flowchart TD Flutter["Flutter Client"] -->|"HTTP · DTO contract only"| Api["Api (/api/v1)"] ServerUI["Server.UI (Blazor Admin)"] --> Application Api --> Application Infrastructure --> Application Application --> Domain Infrastructure --> Domain
Dependencies point inward.
Domain ← Application ← {Infrastructure, Server.UI, Api}. All business logic lives in Application.
Client is a separate bounded context.
The Flutter app depends only on the versioned DTO contract — never the DB, Blazor, or domain types.

Backend layers already exist as a .NET 10 template. This spine adds only the Api project and the Flutter client.

The three calls that matter most

If we get only three things right…

AD-2 · AD-3 · AD-12

One API boundary

The client talks only to a versioned REST API that delegates to the shared Application layer. No bundled content, no second code path.

AD-4 · AD-5 · AD-6 · AD-11

Server owns fidelity

Composition, randomisation, scoring, pass/fail, and timing are computed server-side. The client renders and collects — never grades.

AD-10 · AD-13

Anonymous by design

A self-custodied UUID is the learner's whole identity — no accounts, no PII. Admin auth stays a separate domain.

Everything else in the spine protects one of these three from drifting.

The heart — test fidelity

Why grading never happens on the phone

AD-4 — Server computes
Composition + scoring live in Domain/Application. Client renders results verbatim; never re-computes or caches a grade.
AD-5 — Immutable snapshot
An attempt freezes its questions + a per-section display_order at start. Resume returns the identical order; edits never touch a live attempt.
AD-6 — Answers withheld
Test mode ships no correct keys; the server returns only per-section/per-code results. Practice may show correctness — still server-owned.
AD-11 — Config, not code · server clock authoritative
Counts, pass marks, time limits, sections are seeded data. Elapsed time is computed server-side from started_at; a client submitted_at is diagnostic only.

These four were tightened by the adversarial review to close cross-team divergence (randomisation authority, results shape, timing, Practice grading).

Content & the sign catalog

One authoritative source of truth for content

AD-7

Signs are seeded reference data

legislation_code is a unique key. Questions reference a sign by sign_ref — resolved exactly-once, never an embedded image or ad-hoc label.

AD-8

Import validates before it stores

Every CSV/JSON row is checked against schema and catalog. A bad row is rejected with its position — never partially stored.

AD-9

Two-axis content model

Each question carries its code(s) and a shared/code-specific class, plus a language_code. Sections are fixed order; randomisation is intra-section only.

AD-9

Combinations compose once

Code 1+2 or 1+3 answer the shared sections once and add one Vehicle-Controls module per selected code — graded independently.

Deferred & open

What we deliberately did not decide

Deferred down

Open questions

AD-11 makes the fidelity numbers configurable, so the unconfirmed counts and time limits can land late without a structural change.

Let's discuss

Decisions to pressure-test together

1 · Offline sittings

Online-first keeps grading server-authoritative. Is offline practice a v1 need? It would add a client attempt store and a sync boundary.

2 · Sign assets

Images from MinIO vs bundled in the app? Affects app size, offline, and the sign-catalog delivery contract.

3 · Admin auth model

Who may author vs publish vs import? AD-13 assumes "authenticated admin" — the real role split is still open.

4 · Fidelity numbers

Counts, pass marks, time limits are provisional. Who confirms them against a live DLTC/CLLT terminal, and when?
